The Anchor Repair

The step-level baseline is only as good as its notion of “the same state.” Ours read that identity straight off the observation text — so every failed action in the batch became one state, and every heated egg was indistinguishable from an unheated one. This arm adopts G²PO's anchor construction, and nothing else.

01 — what the anchor is

Two strings leave the environment, and only one of them is the prompt

Every call to AlfWorldEnvironmentManager.step() returns a dict with both text and anchor. They are not the same string and they do not serve the same purpose. Confusing them is the reason this defect survived so long.

textpolicy input

What the agent sees

Task description + last-2 history + observation + admissible actions, assembled by build_text_obs(). This is the prompt tokens go through. The repair does not touch it. Rollouts are affected only through the gradient, never through a changed prompt.

anchorstate identity

What the estimator groups by

Flows into anchor_obs and becomes the node key in g2po_node_values(). Two occurrences with the same anchor are declared the same state and pooled into one value estimate. This is what the arm changes.

The node key, three ways

The task component is the rollout-group uid, so occurrences from different ALFWorld games never pool regardless of text. Everything below concerns the second component only.
02 — where the anchor enters the maths

Four lines decide what a state is worth

Under ccpo_target=nextnode the step credit is not a return — it is the pooled value of the node the action moved into. The anchor therefore sets the target, not merely the comparison pool.

1
NODE[i] = (task[i], str(anchor_obs[i]))
The node key. One string equality test decides whether two occurrences are the same state. No similarity, no embedding — byte equality.
2
VAL[k] = mean over visits i∈k of γ(T−t) · R(traj i)
A node's value is the mean discounted outcome over every visit to it in the batch, across all 8 sibling rollouts. Merge two unrelated states and this average is taken over experiences that have nothing to do with each other.
3
NEXT[i] = NODE[i+1] within the trajectory, else terminal
The successor. TGT[i] = VAL[NEXT[i]] − penalty·invalid[i] is what the step advantage is computed on.
4
if len(members[node]) < 2: continue # advantage stays 0
A singleton node contributes no step credit at all. With one member there is no leave-one-out comparison to make, so the occurrence is dropped from the step term. This is why the singleton count is the statistic everyone watches — and why it is not, on its own, a quality measure.
Why this survives a global gate

This arm runs ccpo_gate=global, where the bucket is the whole task and a continuous affinity does the weighting. It is tempting to conclude the anchor no longer matters. It does: the gate chooses the baseline pool, but the anchor still builds VAL, and VAL is the target. A broken anchor corrupts what the step term is trying to predict, which no amount of baseline smoothing repairs.

03 — the three repairs

One flag fixes two defects, the other fixes a third

G²PO's env_manager.py contains all three. git log -S confirms none was ever in our tree, and GiGPO's original lacks them too — so this is a G²PO contribution, not a regression on our side.

B · the failure collapse — ACG_OBS_REPAIR
The dominant half. ALFWorld answers every illegal action with the same sentence. Taking that sentence as the state pools an agent that failed in the kitchen with one that failed in the bedroom — and then feeds their averaged outcome back as the target for both. Applies to every task type.
A · the invisible state — ACG_OBS_REPAIR
The weaker half, recorded honestly. Our own per-type deficits do not support it: the four pattern-affected types average 77.8 and the two unaffected ones 78.6. Kept because it is part of G²PO's anchor, not because we have evidence for it.
C · the admissible-action disambiguator — ACG_ANCHOR_AFF
Added to the tree on 2026-09-03 with the 42.8% figure attached, and never wired into the node key (core_ccpo.py:795 writes it to the dump; core_ccpo.py:409 builds the key without it). H-AE is the observation that these two facts had never been put together.

read the failures

t=3 and t=7 — repair B

Both raw anchors are the bare string "Nothing happens.". Batch-wide these two turns — one holding an egg in the kitchen, one standing at a heated countertop — would have shared a node with every other failure in all 128 rollouts. After repair they inherit their own last real observation and separate cleanly. 2 of 9 turns collapse without it; 0 after.

read the concatenations

t=6 and t=9 — repair A

t=6 raw is byte-identical to what the same square looks like before the egg was heated — the state changed, the text did not. Prepending the predecessor makes the heat event part of the identity. t=9 shows the same for "You turn on". Distinct anchors go 8/9 raw → 7/9 repaired, which is the point: the count falls because two turns correctly merged onto their true predecessor state.

Order matters, and the code depends on it

When both flags are on, the admissible-action block is appended before the repair logic runs, so the history stores augmented strings. This is safe only because both branch tests — startswith("Nothing happens") and the invisible-pattern test — are prefix tests, which a trailing append leaves intact. Control flow is therefore identical with and without ACG_ANCHOR_AFF. That invariant is what makes the refinement argument in §06 hold.

06 — the one thing the confound cannot touch

anchor_aff can only split nodes, never merge them

The direction of the third column is not an empirical finding. It is forced by the construction, which means it survives the hardware change intact.

∴
key' = f(obs, admissible)   vs   key = f(obs)
Appending a field to a key produces a refinement of the partition: if two occurrences agree on key' they must agree on key, but not conversely. Formally key'[i] = key'[j] ⇒ key[i] = key[j].
⇒
n_nodes' ≥ n_nodes   and   singleton_frac' ≥ singleton_frac
For any fixed batch, on any hardware. Every node either stays whole or breaks into pieces; pieces of size one can only be created, never destroyed.
What this buys and what it does not

The claim “anchor_aff reverses obs_repair's singleton gain” is sound in direction — it needs no clean pairing, because the inequality is a theorem about the key, not a measurement. The claim “by 797 → 1,149 and 0.227 → 0.339” is confounded — the live FLASH run of the same configuration gives 1,116 and 0.298 — and should be re-measured on matched hardware before it is quoted. The precondition is the prefix-test invariant from §04: control flow must not change between the two configurations, or the refinement property fails.

Consequence for the working hypothesis

The step-1 note on the previous launch argued that repair B's singleton drop was the mechanism worth betting on. That story cannot also explain a positive result from this arm, because the pair does not preserve the drop — it ends up slightly above base in node terms and clearly above in occurrence terms. If held-out improves here, the cause is finer, more accurate node identity feeding VAL, not increased pooling. Ablating the halves is therefore mandatory rather than optional, and only worth running if the pair moves the number.

08 — the confound, stated precisely

Three things changed at once, and each alone is sufficient

The comparator was produced on a different machine. This is not a small numerical detail in an agentic setting, and it is worth being exact about why.

Verified rather than assumed: tensor_model_parallel_size=1 appears in both run.sh files, so the earlier “sharding” explanation was wrong — no parameter is split across cards. The data-parallel split is confirmed by the metrics: global_seqlen/mean went 898,233 → 1,846,313 (×2.06) while perf/total_num_tokens held at 3.59M → 3.69M (×1.03) — same total work, half the workers, double each. TRITON_ATTN has no capability gate in vLLM 0.11 (platforms/cuda.py:321), so it is honoured on sm_80.
mechanism iRNG position

No per-request seed exists

The engine is constructed with seed=0, but the resolved sampling parameters — read from this run's own log — are {n:1, logprobs:0, max_tokens:512, detokenize:False, temperature:1.0, top_k:-1, top_p:1.0, ignore_eos:False}. No seed key. Sampling therefore draws from one engine-level generator in scheduling order, and a prompt sitting 12th in a 32-sequence batch lands elsewhere in a 64-sequence one.

mechanism iifloat non-associativity

Batch shape selects kernels

Larger per-engine batches change GEMM and attention tile shapes and reduction orders; a different architecture changes the tensor-core instructions and the Triton codegen outright. Logits differ in the last bits — enough to flip a token near a decision boundary.

amplifierchaotic, all-or-nothing

One token ends the pairing

A flipped token changes the action, which changes the observation, which changes every prompt after it. Over ≤50 turns the trajectories become independent draws. A second cause adds nothing on top of the first, so the 7-vs-14 success gap cannot be apportioned between hardware and batch width, and no further analysis recovers it. 7 vs 14 of 128 is ~2.3 sd at p≈0.08 — it needs no bug to explain.

What still holds — and it is the part that matters

build_alfworld_envs(path, seed, train_batch_size=16, group_n=8) has no GPU-count dependence, so both arms play the same games. Pairing exists to control task difficulty, and that control survives. Hardware acts like a seed change — variance, not bias. Held-out comparisons at matched steps remain meaningful; single-step rollout equality does not.

09 — one training step on this box

What actually runs

1

Sample tasks & replicate

16 ALFWorld games from the train split, each replicated ×8 → 128 concurrent episodes, one Ray actor apiece. Built from (seed, 16, 8) — independent of GPU count.

2

Multi-turn rollout (≤50 turns)

Prompt = task + last-2 history + observation + admissible actions → ≤512 tokens of <think>…</think><action>…</action> → parser → env reward (success 10 / invalid −0.1). Rollout temp 1.0; validation temp 0.4. Two vLLM engines, 64 sequences each. 254 s of the 527 s step.

3

Build the anchor — the only thing this arm changes

For each of the 128 environments: append the admissible-action block (ACG_ANCHOR_AFF), then apply the repair (ACG_OBS_REPAIR) — skip the history append on "Nothing happens", and join the last two entries when the predecessor began with "You heat" / "You cool" / "You clean" / "You turn on". Emitted as anchor, alongside the untouched text.

4

Flatten & group

≈6,144 occurrences u=(traj i, turn t). Node keys built from the anchor; VAL, NODE, NEXT follow (§02). γ=0.95.

5

Two advantage terms, one scale

Episode term (group-relative outcome) + step term (successor value under target=nextnode, global gate, edge_w=1.0), both under mean_std_norm so adv_ep_over_cc ≈ 1.

6

PPO update, then evaluate every 5 steps

Token-level PPO, lr 1e-6, kl_loss_coef 0.01 low-var KL. Held-out = 128 rows of test.parquet in two chunks of 64. 131 s update, 15 s advantage.

Structural gain is not accuracy — this has already burned us once

ccpo-hardedge vs ccpo-global moved effect_rel by a factor of a hundred and moved held-out success by −0.01 points over nine paired evaluations. Every grouping statistic in §05 is therefore diagnostic only. Do not promote this arm on n_buckets, singleton_frac or effect_rel.

Two caveats to settle at the first evaluation

1. The shared-draw property — validation envs are Ray actors sized by val_batch_size, not by GPU count, so the draw should match. The code says it holds; it has not been measured on this box. Confirm at step 5 before treating any comparison as paired. 2. Do not quote a stepN-best number. Best-checkpoint selection takes the maximum of a noisy series and is biased up by ~1.5 sd; report the mean over evaluations.
